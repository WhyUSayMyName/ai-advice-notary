# CLAUDE.md — контекст проекта «Иггдрасиль» (ai-advice-notary)

Бренд/отображаемое имя продукта — «Иггдрасиль» (лат. Yggdrasil), мировое древо:
корень якорит данные, ветви — merkle-батчи, ствол — связанный реестр. Слово
«якорь/якорение» осталось названием механизма, не продукта. Код-идентификаторы
(репозиторий `ai-advice-notary`, пакеты, `Notary.sol`, `verifier-cli`) не переименованы.


Система доказуемой фиксации неизменности цифровых данных: документы и телеметрия
хранятся off-chain у владельца, во внешний реестр (блокчейн) якорится только
SHA-256-хеш. Внешний аудитор постфактум доказывает подмену или уничтожение данных,
**не доверяя оператору хранилища** — это центральное свойство, ради которого
принимаются все архитектурные решения. Система обнаруживает нарушения, а не
предотвращает их. Формализованная модель угроз и план экспериментов — в docx-архиве
исследования (вне репозитория); публичный план — в `ROADMAP.md`.

## Структура репозитория

| Путь | Что это |
|---|---|
| `contracts/Notary.sol` | Единственный контракт: append-only реестр `notarize(hash)` + `anchorRoot(root, leafCount)` |
| `scripts/deploy-notary.ts` | Деплой; пишет `NOTARY_ADDRESS` в оба `.env` и экспортирует ABI в приложение |
| `test/` | Тесты контракта (hardhat) |
| `blockchain_notary/` | Electron + React десктоп-приложение |
| `blockchain_notary/src/main/*-core.ts` | **Ядра без Electron** — вся логика живёт здесь |
| `blockchain_notary/src/mcp/` | MCP-сервер (нотаризация LLM-диалогов и аттестаций) |
| `verifier-cli/` | Независимый верификатор аудитора — отдельный мир, см. ниже |

## Архитектурные принципы (не нарушать)

1. **Ядра свободны от Electron.** `database-core`, `anchor-service`, `merkle-core`,
   `evidence-core`, `dialog-canon`, `attestation-canon`, `canonical-json` не импортируют
   `electron`. Electron-модули (`database.ts`, `anchor.ts`, `version-chain.ts`) — тонкие
   обёртки. Новая логика добавляется в ядро с DI (см. `ChainAdapter`, инъекция `now()`),
   обёртка только связывает. Это делает всё тестируемым в vitest и переносимым
   в будущий headless-сервис (ROADMAP, phase 7).

2. **Верификатор не должен доверять этому репозиторию.** `verifier-cli/verify.mjs` —
   один читаемый файл, одна зависимость (`ethers`), без SQLite и без общего кода
   с приложением. Аудитор читает его глазами. Не выноси в него общие модули,
   не добавляй зависимости, не усложняй.

3. **On-chain минимализм.** В контракт уходят только `bytes32` (хеш или merkle-root).
   Никаких URI, метаданных, персональных данных — это и приватность, и газ.
   Проверка merkle-пруфов — off-chain (в верификаторе), НЕ в контракте.

4. **Детерминизм канонов — святое.** Любая неоднозначность ломает воспроизводимость
   проверки:
   - `canonical-json.ts`: сортировка ключей, запрет NaN/Date/функций (ошибка, не искажение);
   - merkle: `leaf = SHA-256(0x00 ‖ h)`, `node = SHA-256(0x01 ‖ min ‖ max)` (доменное
     разделение против second-preimage, сортированные пары — пруф без флагов лево/право),
     нечётный узел поднимается без пары (не дублируется — CVE-2012-2459), всюду SHA-256;
   - цепь эпох: `Cₙ = SHA-256(0x02 ‖ Cₙ₋₁ ‖ rootₙ)`, префикс 0x02 отделяет звено
     от узла дерева; пары НЕ сортируются — здесь порядок значим, он и есть время.
     On-chain уходит `Cₙ`, а не голый корень пакета;
   - форматы версионированы: `notary-dialog/v1`, `notary-attestation/v1`,
     `notary-evidence/v3`. Изменение формата = новая версия + обратная совместимость,
     старые форматы никогда не перестают проверяться.

5. **Anchor-воркер последовательный.** Один in-flight запрос — нет гонок nonce.
   Перед КАЖДОЙ отправкой — `isNotarized` (дубликаты on-chain невозможны).
   Recovery при старте сверяет незавершённые записи с чейном (по хешу и по
   заякоренному значению эпохи). Масштабирование — через merkle-батчи, не через параллелизм.

6. **Одно подключение к узлу на приложение** (`notary.ts`). Провайдер держит
   соединение и цикл переподключения; раньше он создавался на каждый вызов, и
   брошенные экземпляры стучались в узел до конца сессии. Там же
   `cacheTimeout: -1`: кэш ethers на ~250 мс возвращал один и тот же nonce
   двум подряд идущим транзакциям. Чтение реестра ключа не требует —
   контракт с подписантом создаётся лениво.

7. **Очередь в SQLite — источник истины**, переживает падения. База общая между
   Electron-приложением и MCP-сервером → WAL + busy_timeout уже включены
   в `createDatabase`, не отключать. Имя каталога данных задано ОДИН раз
   в `app-paths.ts` и обязано совпадать с `name` в `package.json` (оттуда его
   берёт Electron) — тест `app-paths.test.ts` это стережёт. Разойдутся —
   приложение и MCP молча начнут писать в разные базы.

8. **Ключ подписи только в защищённом хранилище ОС.** `key-store-core.ts` —
   ядро с инъецируемым шифром, `key-store.ts` — обёртка над `safeStorage`
   (DPAPI / Keychain / libsecret). Ключ НИКОГДА не уходит в renderer, в IPC-ответ
   и в лог: наружу отдаётся только `KeyStatus` с адресом подписанта.
   `NOTARY_PK` в окружении остаётся запасным вариантом для разработки и e2e,
   но интерфейс обязан показывать это тревожным цветом — иначе оператор уедет
   в прод с ключом открытым текстом. У MCP-сервера ключа нет вообще: он только
   кладёт хеши в очередь, якорит приложение.

## Инварианты данных

- Хеш файла: `0x` + 64 hex, SHA-256 **от байтов файла** (`sha256FileHex`).
  Канонизированный диалог/аттестация СТАНОВИТСЯ файлом — поэтому весь конвейер
  (очередь, батчи, evidence, аудит, верификатор) работает с ним без спецслучаев.
  Сохраняй это свойство: новый тип артефакта = новый канон → файл, а не новая ветка кода.
- БД: `UNIQUE(artifact_id, hash)` — одинаковый контент в разных артефактах разрешён,
  внутри одного — конфликт (`HashConflictError` со `conflictVersion`) либо `unchanged`,
  если совпал с последней версией. Молчаливых `INSERT OR IGNORE` в проекте нет — не возвращать.
- Версии связаны `previous_hash`; целостность цепочек проверяет `version-chain-core`.
- Каждая фиксация помнит свой **реестр** — `"<chainId>:<адрес контракта>"`
  (`registry-core.ts`): колонка `registry` у `anchor_queue` и `anchor_batches`,
  ключ пакетов — `(root, registry)`. Цепь эпох своя у каждого реестра (генезис
  в новой сети, а не голова старой). Аудит, эпохи, сертификат и пакет
  доказательств смотрят только в текущий реестр: документ из другой сети —
  `OTHER_REGISTRY`, а не «нет в реестре». Иначе смена сети неотличима от подмены.
  Пакеты до учёта реестров хранят `''`; recovery при старте находит их on-chain
  и проставляет реестр, не найденные в аудите — `REGISTRY_UNKNOWN`.
- PDF-сертификат (`certificate.ts`) обязан показывать ЗАЯКОРЕННОЕ значение, а не только
  хеш документа: при пакетной фиксации в реестре лежит голова цепи, и аудитор, который
  пойдёт искать там хеш файла, ничего не найдёт. Поэтому в `CertificateData` приходит
  блок `batch` (корень, merkle-путь, связка эпох), а хеши печатаются целиком — обрезать
  их многоточием нельзя, по ним сверяют. Шрифты — Fira Sans/Mono (OFL) в `public/fonts`,
  оттуда vite кладёт их в `dist`, который единственный попадает в установщик; встроенные
  шрифты PDF не годятся — в них нет кириллицы.
- ABI контракта: единственный источник — `blockchain_notary/src/main/abi/Notary.json`,
  генерируется `deploy-notary.ts` из hardhat-артефакта. Не редактировать руками,
  не хардкодить строки ABI в коде.

## Сборка и тесты

```shell
npm install && cd blockchain_notary && npm install

# всё сразу: hardhat node + деплой + приложение
cd blockchain_notary && npm run dev:all

npx hardhat test                      # контракт (из корня)
cd blockchain_notary && npm test      # vitest-ядра
npx tsc                               # типы приложения (noEmit)
npm run build:mcp                     # MCP-сервер → dist-mcp/server.mjs
```

Живые e2e (нужен поднятый узел + деплой):
`E2E_RPC_URL=... E2E_NOTARY_ADDRESS=... E2E_PK=... npm test`

**Деплой.** Сети объявлены в `hardhat.config.ts`, переменные — в корневом
`.env` (шаблон `.env.example`), он же читается через `dotenv/config`.

```shell
npm run deploy:local            # нужен запущенный npx hardhat node
npm run deploy:sepolia          # нужны SEPOLIA_RPC_URL и DEPLOYER_PK
npm run verify:sepolia -- <адрес контракта>
```

`DEPLOYER_PK` — ключ, которым контракт РАЗВОРАЧИВАЕТСЯ, он лежит открытым
текстом и потому обязан быть одноразовым. Ключ, которым приложение ЯКОРИТ,
живёт в защищённом хранилище ОС и задаётся в интерфейсе — это разные ключи,
и путать их нельзя. Контракт permissionless: якорить может любой аккаунт,
совпадение с деплойщиком не требуется.

Верификация на Etherscan — не украшение: модель угроз требует, чтобы аудитор
читал РАЗВЁРНУТЫЙ код, а не верил оператору, что задеплоено то же, что в репо.

**Сборка установщика на Windows.** `npm run build` падает при распаковке
`winCodeSign`: в архиве есть macOS-симлинки, а Windows не даёт их создать без
Developer Mode или прав администратора. Обход — заранее положить распакованный
архив в кеш (симлинки при этом просто не создаются, на Windows они не нужны):

```shell
CACHE="$LOCALAPPDATA/electron-builder/Cache/winCodeSign"
7za x -y "$CACHE/<любой скачанный>.7z" "-o$CACHE/winCodeSign-2.6.0"
```

Иконка собирается из фирменного знака: `node scripts/make-icon.mjs` даёт
`build/icon.pdf`, из него растрится `build/icon.png` (он в git — сборка не должна
требовать Python), остальное electron-builder делает сам.

**Ловушка better-sqlite3:** основная копия собрана под ABI Electron. Всё, что
работает в чистом Node (vitest, MCP-бандл), использует алиас `better-sqlite3-node`
(vitest.config.ts / scripts/build-mcp.mjs). Любой `npm install` в
`blockchain_notary` ставит для `better-sqlite3` prebuild под ABI текущего Node
и тем самым ломает приложение — тесты при этом продолжают проходить, потому что
идут через алиас, так что заметить это по зелёному прогону нельзя. Лечится не
`npm rebuild`, а загрузкой prebuild'а под Electron:

```shell
cd blockchain_notary/node_modules/better-sqlite3
npx prebuild-install -r electron -t 30.5.1
```

Проверка (бинарник грузится ЛЕНИВО, в конструкторе — простой `require` проходит
всегда и ничего не доказывает):

```shell
node -e "new (require('better-sqlite3'))(':memory:')"       # должно упасть: ABI 123 против 137
node -e "new (require('better-sqlite3-node'))(':memory:')"  # должно пройти
```

**MCP-сервер — stdio:** stdout принадлежит JSON-RPC. Любой вывод — только в stderr
(баннер esbuild уже перенаправляет console.log). Не добавлять console.log в код,
попадающий в бандл сервера.

## Конвенции

- Комментарии в коде приложения — по-русски; комментарий объясняет ограничение
  или намерение, а не пересказывает строку.
- Тесты рядом с кодом в `__tests__/`; для ядер — обязательны. Тесты шагают через
  `processNext()` и инъецированные часы — таймеров и sleep'ов в тестах нет.
- `.env` не коммитится (в git-истории его никогда не было — сохранять это).
  Шаблон — `blockchain_notary/.env.example`.
- Коммиты: `feat:`/`chore:`/`docs:` + содержательное тело; пуш в `main` на
  github.com/WhyUSayMyName/ai-advice-notary.
- Дизайн UI утверждён: язык Linear (тёмный графит, индиго #5E6AD2, обе темы) —
  макет в артефакте, стиль переносится в React-компоненты при декомпозиции App.tsx.

## Границы MVP (осознанно НЕ делаем сейчас)

- Проверку merkle-пруфов on-chain — верификация off-chain by design.
- Внешнее хранение ключа подписи (HSM / KMS). Ключ уже в защищённом
  хранилище ОС (принцип 8); `NOTARY_PK` в окружении — только для разработки и e2e.
- Параллельные anchor-воркеры.
- Второй контракт / изменение схемы `Notary.sol` без крайней необходимости.
- Хранение оригиналов данных где-либо, кроме машины оператора.

Критерий добавления фичи (по Founder's Playbook): реальный сигнал от пользователей
или требование модели угроз — не «легко же добавить».
